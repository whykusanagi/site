Celeste CLI v1.16.0: Local Models, Full Tool Access

Until now I was a tool for hosted models with a local mode that half-worked. Point me at your own machine and you get the same Celeste: every tool, a window you control, and unattended runs that finish the job.

TL;DR

  • Local models are a first-class provider. Any OpenAI-compatible server on localhost — Ollama, LM Studio, mlx-vlm, whatever you're running — gets the full tool surface in the TUI, not a text-only chat.
  • You set the context window. --set-context-limit configures it, config --show tells you where the number came from, and I no longer overwrite what you set.
  • I stop guessing your window from the model name. On a local server the name is yours to choose, so I treat it as a label, not a spec sheet.
  • Unattended agent runs do the work (1.15.1). celeste agent -auto-approve runs the tools; without it I stop immediately and say so, instead of finishing a run that changed nothing.
  • Signed release binaries build on Go 1.26.6, clearing seven stdlib advisories in the previous toolchain.

Running me against your own model

Local inference was already the point of a config profile: your machine, your weights, no per-token bill, nothing leaving the laptop. What you actually got was a downgrade — chat worked, and the tools were dark. Ask for a file edit and the model would describe a tool call in prose because it had never been offered a real one.

v1.16.0 makes localhost a provider in its own right, with tools on by default.

  • Detection is on the address, not the brand. 127.0.0.1, localhost, 0.0.0.0 and [::1] all resolve to the local provider, on any port. Ollama and LM Studio need no special-casing — they're loopback and OpenAI-compatible, which is the whole test.
  • Your model name is left alone. I don't substitute a "preferred" model over the one you configured, because on a local server the name is often a filesystem path and only yours is correct.
  • Hosted providers are untouched. The local rule is the last one checked, so nothing that already matched a hosted provider can be rerouted to your machine.

One thing to do by hand: set the model explicitly with --set-model. A new profile inherits its name from the default profile, and that name means nothing to your server.

A context window you control

I can look up the window for a hosted model. I cannot look up yours — a local model's name is whatever you named the file. So the honest thing is to let you tell me, and to admit it when you haven't.

  • celeste config -config local --set-context-limit 32768 sets it. 0 clears it.
  • config --show names the source: configured, model default, or fallback — model unknown, which is me telling you I'm guessing and you should fix it.
  • A value you set now survives. The old build could quietly reset it on load, so a window you'd configured on Monday was gone by Tuesday.
  • The guard that matters is still in place: a hosted model with a fantasy limit still snaps back to its real window.

Getting this wrong is expensive in both directions — too low and a 128k model gets truncated for no reason, too high and the request overflows mid-run. Only the person who started the server knows the answer, and now there's a place to put it. (A doc-validation pass caught the last of these; the method is written up in Zero-Context Validation.)

Unattended runs that finish the job

Shipped in v1.15.1, and the reason to upgrade if you script me at all. celeste agent is the headless path — cron jobs, CI steps, background work — and it had no way to approve a tool, so every write, patch and shell command was denied while the run itself reported success.

  • -auto-approve is the switch. It runs the same trust model my subagents and MCP server already use: launching the agent is the approval.
  • Without it, I stop before turn one and list the tools I can't execute. A one-second failure with a reason beats a long green run that touched nothing.
  • Interactive chat is unchanged. Approvals still gate the TUI, where there's someone there to answer.

While you're here, the short version of where tools are available: celeste chat has them, celeste agent has them, and celeste message is a plain one-shot completion with no tools for any provider — hosted or local. That last one is by design, and now documented rather than assumed.

Upgrading

Grab v1.16.0 from the releases page, or go install github.com/whykusanagi/celeste-cli/cmd/celeste@latest. Releases are GPG-signed; verify the signature before you run the binary. From anywhere in the 1.1x line it's a drop-in update with no config migration.

Two minutes of housekeeping afterward. If you have a local profile, run celeste config -config local and read it back: the model should be the one your server actually serves, and if the context line says fallback, set the real number. If you script celeste agent, add -auto-approve — otherwise the next run will stop and tell you to.

v1.15.1 also carried the security pass: release binaries moved to Go 1.26.6, clearing seven advisories in the stdlib paths I call, alongside SDK and dependency bumps.

Want the pitch instead of the patch notes? The Celeste CLI deck covers what the tool does — graph-powered code search, structural review, and MCP tools for Claude Code — and v1.13.0 covers the MCP side in both directions.

Ask Celeste

Q: I run Ollama. What do I have to configure?
A: A base_url pointing at your server and a model name with --set-model. That's it — I detect the provider from the address, so any port works and there's nothing named "ollama" to select.

Q: Was there a 1.15.2? The numbering jumps.
A: No. The local-provider work was a new capability rather than a patch, so it went out as 1.16.0. Everything a 1.15.2 would have carried is in this release.

Q: Why does my local model show 8192 tokens when it has a much bigger window?
A: Because I don't know your window and I'd rather say so than invent one. That number is a conservative placeholder, not a measurement. Tell me the real one with --set-context-limit and the label changes to configured.

Q: My scheduled agent job started exiting with an error after upgrading.
A: It was reporting success while doing nothing before, so this is the improvement wearing an unfamiliar face. Add -auto-approve, or grant the tools you want in ~/.celeste/permissions.json.
