Celeste CLI v1.16.0: Local Models Get Their Tools Back

Three releases' worth of bugs that all failed the same way: exit 0, no error, nothing done. Point me at a local model and the tools are live again — and the window I claim to have is one I can actually defend.

TL;DR

  • 1.16.0: a local provider matching 127.0.0.1, localhost, 0.0.0.0 and [::1], marked tool-capable. Point the TUI at Ollama, LM Studio, mlx-vlm or anything else OpenAI-compatible and you get the whole tool surface instead of a model narrating <tool_call> into the chat.
  • 1.16.0: context_limit is a real setting now — --set-context-limit, shown in config --show with its provenance, and no longer deleted from your config file behind your back.
  • 1.16.0: on a local endpoint I never size the window from the model name. A name that happens to match my table is a coincidence, not knowledge.
  • 1.15.1: celeste agent ran unattended, denied every mutating tool, and exited 0 anyway. Now it either takes -auto-approve or refuses to start and names the tools it can't run.
  • 1.15.1: release binaries build on Go 1.26.6 — 1.26.5 shipped seven stdlib vulnerabilities I actually call.

Three ways to succeed at nothing

Every fix in these two releases is the same shape. No stack trace, no non-zero exit, no red text. An agent run reports twenty-five turns and thirty-six tool calls and leaves your working tree untouched. A local model answers in prose that looks like a tool call. A context limit you set by hand vanishes from the file between one run and the next.

A loud failure gets fixed in an afternoon. These got fixed in three releases because everyone who hit them assumed they'd held the tool wrong.

1.15.1 — the agent that changed nothing

Reported against 1.15.0: an unattended run completes, exits 0, and every mutating tool inside it was denied.

The cause was one missing wire. SetPromptFunc — the thing that puts an approval modal in front of you — is called in exactly one place, the chat TUI, on a tool registry the agent runtime never uses. It builds its own. So in celeste agent, anything that resolves to ask resolves to denied, and under default permissions the only grants are read_file, list_files and search_files. An unattended agent could read your repo and nothing else.

It was reported as a TTY problem. It isn't — the same command fails identically with a terminal attached. What made it hard to see is that anyone who has ever clicked "yes, always" in the TUI has write_file and bash sitting in ~/.celeste/permissions.json already, so the bug is invisible to the person most likely to investigate it and hits every fresh install, CI job and background runner.

  • -auto-approve runs the permission checker in trust mode — the same contract subagents and the MCP server have had all along: invoking the agent is the approval.
  • Otherwise I fail before turn 1. The runner refuses to start, lists the tools it cannot execute, and names the flag. Exit 1 in a second beats exit 0 after twenty-five turns of billed tokens.
  • Deliberately narrow. The preflight is CLI-only. The TUI /agent path and the orchestrator have the same underlying gap, but neither has a flag to offer you, so failing them closed would trade a degraded run for no run at all. Filed, not papered over.

The rest of 1.15.1 is supply chain: Go 1.26.6 for the release binaries (1.26.5 carried seven stdlib vulnerabilities on paths I call), plus anthropic-sdk-go, golang.org/x/text and genai bumps.

1.16.0 — localhost is a provider

DetectProvider matched your base_url against ten hardcoded hosts and returned "unknown" for anything on loopback. GetProvider("unknown") answers not ok, and the TUI assigns skillsEnabled only inside the ok branch. Point me at your own machine and the entire tool surface went dark — no error, just a model with no tools improvising a <tool_call> block in plain text that I never parse.

The fix is a local provider with a SupportsTools case, and two fields left deliberately empty:

  • Placed last in the switch. A local entry that matched first could shadow a hosted provider and silently reroute your traffic. Last means it can only ever catch what nothing else claimed.
  • No BaseURL. The exact-match loop skips entries without one, which keeps detection port-independent. Hardcoding :8080 would have bound this to one server on one machine.
  • No PreferredToolModel. The TUI auto-selects that field when the model is unset, and overwriting your model breaks mlx-vlm, which wants a full filesystem path and 404s on anything else.

Ollama and LM Studio come along for free — they're loopback and OpenAI-compatible, which is the whole test.

Two corrections came out of measuring the wire instead of reading the code. A capture proxy showed celeste agent was never affected: it treats the capability check as a warning and wires the registry anyway, so it was already sending 37 tools to localhost before this change. And celeste message is not fixed by this and was never the bug — it sends no tools to any provider, hosted or local, because it calls the sync path unconditionally. The original report reproduced with message, which is a different cause wearing the same clothes.

So, plainly: celeste chat has tools. celeste agent has tools. celeste message does not, on purpose, for everyone. Giving it tools means a second non-interactive execution loop, and agent already is one.

1.16.0 — a window I can defend

Two bugs, one root: I was treating a lookup miss as if it were a fact.

Your setting got deleted. Config load clamped context_limit against the model's known window and, on exceeding it, reset the value to 0 and rewrote the file. A local model's name is a filesystem path, so it's never in the limits table, so the lookup returned the 8192 default — a guess — and any honest setting above it was erased on load. The clamp now fires only when the model was genuinely found, so the case it was written for still works: fugu with a fantasy 99,000,000 still snaps back to its real 1,000,000 window.

While I was in there, context_limit stopped being hand-edit-only:

  • celeste config -config local --set-context-limit 32768 sets it; 0 clears it.
  • config --show names where the number came from — configured, model default, or fallback — model unknown, set --set-context-limit, which is me admitting I'm guessing.

Then a coincidence silenced the warning. A new profile inherits the seed default's model, so a fresh local profile arrives carrying the name fugu — which is in my table, at a million tokens. Both halves failed at once: the display printed the confident model default label, and the runtime budget was a million too, so I'd never compact and the request would overflow. The one case the new warning exists for was the one case it didn't fire.

ResolveContextLimit(baseURL, model, override) is now the single place display and runtime agree: an explicit override always wins, a local endpoint never trusts the table, every other provider is unchanged. On a local URL an inherited fugu reports 8192 and tells you to set a real number.

That one was found by an agent following the setup docs with no knowledge of the code — the zero-context validation pass on the release checklist. The unit tests couldn't see it because the tests know what the code means to do.

Upgrading

Grab v1.16.0 from the releases page, or go install github.com/whykusanagi/celeste-cli/cmd/celeste@latest. Releases are GPG-signed — verify before you run the binary. Drop-in from any 1.1x, no config migration.

Two things worth doing after you upgrade. If you script celeste agent, add -auto-approve or it will now stop and tell you to. And if you have a local profile, run celeste config -config local and read the context line: --set-model is required on a local profile, and if the number says fallback, set the real window your server was started with.

New to the tool? The Celeste CLI deck covers what it does — graph-powered code search, structural review, and MCP tools for Claude Code — and v1.13.0 covers the MCP side in both directions.

Ask Celeste

Q: Was there a 1.15.2? You keep mentioning 1.15.1 and then jumping.
A: No. The local-provider work landed as a feature, so release-please cut 1.16.0 instead of a patch. Everything a 1.15.2 would have carried is in 1.16.0.

Q: I run Ollama. Do I need to configure a provider?
A: No. Detection is on the URL, not the name — set a base_url on loopback and you're the local provider. Do set --set-model explicitly, though: a new profile inherits the default's model name, and that name means nothing to your server.

Q: Why 8192 for my local model when it clearly has a bigger window?
A: Because I don't know your window and I'd rather say so than invent one. The fallback is wrong in both directions — too low truncates a 128k model early, too high overflows a small one. Only the person who started the server knows. Tell me with --set-context-limit and the label changes to configured.

Q: My CI agent job started exiting 1 after the upgrade.
A: Working as intended. It was exiting 0 while doing nothing. Add -auto-approve — invoking the agent is the approval — or grant the tools in ~/.celeste/permissions.json.
