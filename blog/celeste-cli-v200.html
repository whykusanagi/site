Celeste CLI v2.0.0: Safer Edits, a Sharper Code Graph, Your Editor

1.16 made your own models first-class. 2.0 is the major release: every mode runs on one tool loop, every edit can be taken back, the code graph understands what it indexes, and I can work inside your editor instead of beside it.

TL;DR

  • New install path. The module is now /v2: go install github.com/whykusanagi/celeste-cli/v2/cmd/celeste@latest. A go install build swaps itself for the signed release binary on first run, and celeste update keeps it current.
  • Edits you can take back. I read a file before I change it, write atomically, and checkpoint every change to disk, so /undo, /rewind and celeste revert work, even after a restart.
  • A code graph that knows what it's looking at. Go call edges come from the type checker, and release binaries now carry tree-sitter for TypeScript/JavaScript, PHP, Python, Rust, Java, C/C++ and Ruby. Review stops calling your public API dead code.
  • More ways in, each one asked for. Hooks, project MCP servers and sandbox settings from a repository run only after you approve them, and a no is remembered. celeste acp puts me in Zed and JetBrains.
  • Long sessions hold together. A compaction ladder that keeps the state that matters, reasoning kept across turns on Anthropic and OpenAI, and sessions listed by project.
  • An opt-in OS sandbox for shell commands: seatbelt on macOS, bubblewrap on Linux.
  • Reviewed before the tag. Two independent reviewers, rounds of fixes, signed release tags checked in CI, and every GitHub Action pinned to a commit.

A new address, and binaries that keep themselves honest

Go puts the major version in the import path, so 2.0 lives at github.com/whykusanagi/celeste-cli/v2. The old path isn't broken; it just keeps serving the 1.x line, and the last 1.x release mentions, at most once a day, where 2.0 went. Install from the new one:

go install github.com/whykusanagi/celeste-cli/v2/cmd/celeste@latest

  • A go install build upgrades itself to the official binary. The first time it runs a real command, it downloads the release binary for the same version, checks the GPG signature and checksums against the release key compiled into me, replaces itself and starts again. One line on stderr says so. If the download fails nothing is replaced, and I try again in an hour. CELESTE_NO_AUTO_UPGRADE=1 opts out, and a build from a checkout never downloads anything.
  • celeste update installs the newest official release, --check only reports it, and neither will ever downgrade you.
  • celeste persona verify tells you which build you're running: it prints official persona: ... and exits 0 on a release binary, and exits 1 with the reason on anything else.
  • Release binaries are now built on each platform's own runner (Linux, macOS and Windows), with CGo, so the tree-sitter parsers ship in all of them. Linux binaries are still statically linked; macOS needs 12 or later, which Go already required.
  • Release tags are signed with the same key as the binaries, so git tag -v v2.0.0 works too.

Why the swap? The binary you run should be the one that was signed, and only the official build carries my full persona. More on that at the end.

The code graph grew up

The graph is what my search, review and impact tools stand on. In 1.x it was good at finding things and too willing to guess about how they connect. 2.0 replaces the guessing where it can.

  • Go calls are resolved with go/types. Two methods with the same name no longer collapse into one, calls through a field, a chain or a method value point at the right function, and interface methods link to the types that implement them. This works in every build, no C compiler needed.
  • Tree-sitter in the release binaries. 1.x release binaries were built without CGo, so every language but Go was parsed with regex. 2.0 ships the parsers for TypeScript (with TSX and JavaScript), PHP, Python, Rust, Java, C/C++ and Ruby. Java, C, C++ and Ruby are indexed for the first time. Every release build runs celeste index selfcheck, which indexes a small multi-language repo and fails the build if the tree-sitter results aren't in the graph.
  • Review that knows library API from dead code. code_review reads each function's own body, so a TODO is reported on the function that holds it, not the one above. "Likely dead code" is no longer said of constructors, init and main, tests, interface implementations, decorator-registered functions, or the exported API of a library package. STUB now means an uncalled function whose body is empty, a lone TODO, or "not implemented", not every one-liner.
  • Lookups find the exact symbol. They accept qualified names in any form the tools print, never cross languages, and qualified calls like ns::func and Class::method get real call edges.
  • Interrupted builds recover. A build that's killed partway resumes instead of leaving you with an empty graph, and only one indexer writes at a time, across processes.

The graph still has limits (closures and function values, for one), and CODEGRAPH.md lists them. But when it says A calls B now, it's usually right, and when review flags something, it's worth reading.

Edits you can take back

An agent that writes files needs two things: discipline before the write and a way back after it. 1.x had some of the first and none of the second. /undo existed and did nothing useful.

  • Read before edit. I refuse to patch, overwrite or append to an existing file I haven't read this session. Creating a new file needs no read. That rule exists so I can't edit from a stale memory of your code.
  • Atomic writes. write_file, patch_file and splice_file write to a temp file and rename it into place (an append still appends in place), so nothing ever sees a half-written file, and a 0755 script stays executable.
  • Better patches. patch_file takes several edits to one file, all or nothing, and tolerates whitespace drift only when exactly one place matches, showing you the diff.
  • Checkpoints on disk. Each change is saved per session, so /undo walks back file by file, /diff lists what the session touched, and celeste revert <file> works from another terminal or after celeste resume. If you edited the file since, I say so and leave it alone until you repeat the command.
  • /rewind [n] takes back your last n prompts: it restores the files those turns changed, ends the chat before them and puts the prompt back in the input box. /fork continues in a copy of the session when you want to try something without losing the original.
  • Plan mode. /plan limits me to read-only tools until I submit an ordered plan for you to approve or send back. Approval turns the steps into todos, and the question defaults to Keep planning, so a stray Enter can't start the work.
  • A permission prompt typing can't answer. In 1.x, the a in a sentence could allow a call. Now a or A only picks an answer and Enter confirms it, and the prompt shows the full command with control characters escaped, so what you approve is what runs.

Two honest limits. Files changed by a bash command aren't restored by /rewind, and a rewind can't cross a /compact summary. Both are stated when they apply.

One loop, and more ways in

In 1.x the chat, celeste agent, MCP chat, subagents and /orchestrate each had their own tool loop with their own rules. In 2.0 they share one, with the same caps, guards, permissions and hooks. Mostly invisible, which is the point: a guard you set up for the chat now protects your agent runs too.

  • Hooks. ~/.celeste/hooks.json or a repository's .celeste/hooks.json runs your commands at PreToolUse, PostToolUse, UserPromptSubmit, Stop, SessionStart, PreCompact/PostCompact and SubagentStop. A hook can block a call, rewrite its input or add context. A repository's hooks run only after you approve them, and changing one asks again.
  • MCP with consent. A cloned repo's .mcp.json used to be able to start its own servers. Now I show the command and ask first, and your answer is stored, a no included, until the server's command, args, env or URL change. celeste mcp list shows every configured server and whether it's approved, declined or pending; celeste mcp trust and untrust change your mind for you.
  • Your editor. celeste acp speaks the Agent Client Protocol, so Zed and the JetBrains IDEs can run me in their agent panel with my tools, hooks and project context. Tool approvals use the editor's own permission prompt, and editor threads can be reopened.
  • Typed subagents. spawn_agent now takes a type: explore (read-only, small model), review (read, git and graph tools) or general. Each hands back a structured {summary, findings, files} result instead of a wall of prose. They share the chat's MCP servers, hooks and code graph, and isolate_worktree still gives a subagent its own git worktree when several are editing at once.
  • Your existing context files. I read AGENTS.md and CLAUDE.md up to the git root, and no longer create .grimoire uninvited.

Long sessions that hold together

A long session is where an agent forgets what it was doing. 2.0 works hard at not forgetting.

  • A compaction ladder. First I prune old tool results (never one the model hasn't seen yet, and you can recall them), then I summarize older history, and /handoff moves to a fresh session when that isn't enough. Each step scales with the context window, so a 32K local model prunes instead of overflowing.
  • Summaries carry real state. A compaction summary includes the todo list, the files the session changed and the voice rule, rendered from my own records rather than from whatever the summarizer chose to keep.
  • Thinking kept across turns. Claude's thinking is sent back on later turns, byte for byte, also after celeste resume. The openai provider now talks to OpenAI's Responses API and keeps a reasoning model's reasoning the same way. Endpoints without that API fall back to Chat Completions on their own.
  • Sessions know their project. Sessions record their workspace, and celeste resume and /session list show this project's sessions first.
  • Slow models are allowed to be slow. timeout is now a stall timeout: a reply that keeps streaming isn't cut off, and a local server left at the default timeout gets 600 seconds of silence before I give up. A cold first turn on a local model no longer fails just for being cold.

A sandbox, when you want one

Approvals and hooks are policy. A sandbox is a wall. 2.0 adds an OS sandbox for bash, off by default so nothing changes until you choose it: "sandbox": {"enabled": true} in ~/.celeste/config.json.

  • macOS uses a seatbelt profile; Linux uses bubblewrap when it's installed. Windows has no sandbox, and I say so.
  • Commands can write only to the workspace, temp and cache directories, the usual build caches and the repository's git directories. "network": false cuts the network.
  • A repository can tighten its own sandbox through .celeste/config.json whenever it likes. Loosening it takes your approval, the same way hooks do.
  • A blocked write's error names the sandbox and the key to change.

Hooks, custom tools and --verify-cmd run outside it, as before. A repository's hooks still need your approval first.

A security pass before the tag

A tool that edits files and runs commands on your machine has to be held to a higher bar than a chat window. Before tagging 2.0, the codebase went through two independent reviewers, CodeRabbit and Aikido's scanners, and through several rounds of fixes until their findings were closed.

  • Staying inside the workspace. File tools, checkpoints, the code graph and subagents hold on to the directory they checked, so a path swapped out after the check is refused, not followed.
  • Private by default. Config, secrets, sessions, logs and everything else under ~/.celeste are readable only by you, and older files are tightened when I load them.
  • What you see is what you approve. Text from the workspace, tools, models and MCP servers is escaped before it reaches your terminal, and web_fetch reaches only public addresses unless you allow private ones.
  • The release pipeline. A release tag must be signed by the release key and on main before any job holding a secret runs, every GitHub Action is pinned to a full commit SHA, and the build uses Go 1.26.9.

None of this changes how you use me. It changes what a hostile repository can do to you while you do.

The persona, sealed

My personality isn't open source. Official release binaries carry it sealed and decrypt it in memory at startup; a build from source runs a short public persona and says so once. That's why the self-update exists, and why celeste persona verify is there to check.

The persona also fits the model's window now, so a small local model gets a smaller cut of me instead of an overflow. Every version ends with the same boundary: my voice is for prose addressed to you. Code, comments, commit messages and file contents stay plain and professional. You'll get attitude in the chat. You won't find it in your diff.

The default provider is still Sakana's Fugu, for the reasons in Fugu vs Grok.

Upgrading from 1.16

Back up ~/.celeste first (cp -R ~/.celeste ~/.celeste-1x-backup): 2.0 removes or renames a few config keys the first time it loads them. Then:

  • Install from the new path: go install github.com/whykusanagi/celeste-cli/v2/cmd/celeste@latest. The old path without /v2 still installs the newest 1.x, never 2.0. Or download a binary from the releases page and verify its signature as before.
  • Check it: celeste version, then celeste update (a go install build installs the official binary), then celeste persona verify.
  • Rebuild your code graph: an index built by 1.x needs celeste index rebuild to pick up the tree-sitter parsers and the newly indexed Java, C, C++ and Ruby files.

Behaviour changes you're likely to hit:

  • Editing a file I haven't read this session is refused with read_file <path> first. Read it, then edit.
  • A repository's hooks, MCP servers and sandbox loosening ask once before they run. Non-interactive runs skip them with a warning; approve ahead of time with celeste hooks trust or celeste mcp trust.
  • I no longer create .grimoire or touch .gitignore. Run /init when you want one.
  • skip_persona_prompt and the classic/claw runtime modes are gone; the keys are removed on load with a note, and the old flags now error. ~/.celeste/celeste_essence.json is no longer read.
  • The openai provider uses the Responses API. Endpoints without it fall back to Chat Completions automatically.
  • CELESTE_API_KEY, CELESTE_API_ENDPOINT and TAROT_AUTH_TOKEN are now read and override the config file. If an old shell profile still exports one, unset it.
  • Custom JSON tools return stdout and stderr combined, capped at 64,000 bytes, and time out after 2 minutes.
  • /plan cancel is gone; /plan off leaves plan mode.
  • A saved session's tool result over 128 KiB is cut to 128 KiB when 2.0 loads it. Copy the session file first if you need the full text.

The full list, with a before-and-after table for each change, is in MIGRATING-2.0.md.

Ask Celeste

Q: I ran go install ...@latest and I'm still on 1.x. Why?
A: Because Go treats /v2 as a different module, so the old path's @latest is the newest 1.x. Install from github.com/whykusanagi/celeste-cli/v2/cmd/celeste@latest. Same binary name, same ~/go/bin.

Q: My go install build replaced itself on first run. Is that safe?
A: It only replaces itself with the official binary of the same version, and only after the GPG signature and checksums check out against the key built into me. If anything fails, nothing is replaced. If you'd rather keep what your toolchain built, set CELESTE_NO_AUTO_UPGRADE=1.

Q: Why won't you patch a file anymore?
A: I will, once I've read it. I refuse to edit a file I haven't read this session, so I'm never changing code from a stale picture of it. Ask me to read it and the edit goes through. In MCP chat, each call starts fresh, so read and patch in the same call.

Q: A repo's MCP server stopped starting by itself.
A: That's on purpose. A cloned repository shouldn't be able to run a command on your machine just because you opened a chat in it. Approve the server once when I ask, or run celeste mcp trust <server>. Your home-level MCP configs need no approval.

Q: My code graph doesn't show my Java or C++ files.
A: Your index was built by 1.x, which skipped them. Run celeste index rebuild once. A plain celeste index only updates what's there.
